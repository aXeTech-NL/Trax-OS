## Lifecycle

- `designed`: accepted repository design exists.
- `implemented`: the whole row exists in isolation.
- `integrated`: the whole row is wired through its required production-facing layers.
- `validated`: immutable/repeatable evidence exists and every gate stated by the row passes.

Status applies to the whole capability row, never to a partial foundation. Spike observations use their more conservative evidence vocabulary in the linked evidence record and cannot promote production capabilities.

## Maintenance rules

1. Update every affected row in the same pull request as its evidence or requirement change.
2. Promote only with repository evidence plus immutable commit or CI attestation; mutable local success is not `validated`.
3. Regress a status when evidence or a stated gate is invalidated.
4. Keep capability and slice IDs unique; split a row when one issue has independently reviewable gates.
5. Do not copy volatile issue metadata or infer status from an issue being open or closed.
6. State migration impact explicitly, including `None`.
7. Link-check every update and review the cited evidence revision.
8. Re-review affected rows when canonical architecture, roadmap gates, evidence documents, production contracts, migrations, or client-support claims change.
9. Add an automated validator or CODEOWNERS rule separately if approved; do not widen a delivery slice only to add governance tooling.
